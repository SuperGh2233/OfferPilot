# Runbook: main 推送、tag 与更新说明

状态：active；2026-10-09。用户约定：以后要求推送时，包含合并到 `main`，尽量打 tag 并标注更新。此约定适用于后续推送请求，不自行触发推送。

## 前置条件

- 核对工作区、当前提交、远端和待合并范围，保留无关文件；不把未跟踪产物或密钥加入提交。
- 实现改动须按 AGENTS/PLAN 完成 Node 与 lint/typecheck/test/build 验收。仅文档改动检查差异、链接与格式，不重复运行与文档无关的质量门。
- 判断 `main` 推送是否会自动部署；对本次变更适用的迁移、真实账号/RLS 和发布验收要求取得证据。缺证据时具体说明，不能把开发分支推送作为已完成 main 推送。

## 正常流程

1. 获取最新远端 `main` 与 tags，确认没有覆盖他人的提交；把已授权、已验收改动整合进 `main`。可快进时快进，需要合并时保留合并记录；冲突解决后的代码重新运行相应质量门。
2. 将本次可见更新写入 `CHANGELOG.md`，以即将使用的 tag 为标题，列出新增/调整/修复、验证证据及部署待办。内容与最终合并结果一致。
3. 默认 tag 为 `release-YYYYMMDD.N`：上海日期，同日从 1 递增，核对本地和远端均无重名。创建指向最终 `main` 提交的 annotated tag；注释包含更新摘要、测试结果、迁移状态和已知待验收项。多行注释使用临时文本文件及 `git tag -a <tag> -F <文件>`。
4. 显式推送 `main` 与该 tag，优先使用 `git push --atomic origin main <tag>`；若远端不支持原子推送，先推送 main 再推送该 tag，并分别确认。失败须核对远端实际状态后再处理，不强推、不移动已发布 tag、不推送所有历史 tags。
5. 用 `git ls-remote` 核对远端 main 和 annotated tag 的 peeled commit 均等于目标提交；在回复中提供 main 提交、tag 链接和简短更新说明。观察到的部署/Smoke 状态单独报告，源码 tag 不作为生产验收证据。

若特殊情况未打 tag，明确记录原因，并在条件恢复后为同一已推送提交补上 tag；不把“尽量”作为常规跳过的理由。不自动创建 GitHub Release 或修改账号/部署设置。

## 失败与恢复

- 远端 main 前进：重新整合最新提交，处理冲突并验证后再推送。
- main 已成功、tag 失败：确认 main SHA 与目标一致，补推准确指向该提交的新 tag。
- tag 重名：保留已发布 tag，使用同日下一个序号。
- 已发布改动需回滚：在 main 上创建可审查的 revert 提交，经适用验收后推送并创建新 tag；保留旧 tag 与历史。数据库回滚另按相应迁移恢复方案执行。
